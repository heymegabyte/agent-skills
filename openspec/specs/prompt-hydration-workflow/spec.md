# prompt-hydration-workflow Specification

## Purpose

Turns every engineering request into a proportionate, evidence-backed intended-outcome contract and carries material work through architecture, implementation, verification, learning, and convergence.

## Requirements

### Requirement: Prompt Hydration is the first engineering stage
The system SHALL name and execute **Prompt Hydration** before planning or mutation, scaled to the request while preserving the verbatim request and explicit constraints.

#### Scenario: Narrow bug fix
- **WHEN** a user requests a focused defect repair
- **THEN** hydration records relevant context, impact, regression evidence, and improvement review without inventing a product redesign

#### Scenario: Material product request
- **WHEN** a request changes product behavior, architecture, security, integrations, or migration state
- **THEN** hydration maps complete journeys, states, quality concerns, dependencies, reusable ownership, operations, and acceptance evidence before execution

### Requirement: Hydration produces sparse complete coverage
The system SHALL record applicability and gaps across repositories, capabilities, personas, journeys, surfaces, states, and quality concerns without blindly materializing irrelevant combinations.

#### Scenario: Coverage concern is inapplicable
- **WHEN** a coverage dimension cannot affect the intended outcome
- **THEN** the matrix records it as inapplicable with a concise basis rather than generating work

### Requirement: Architecture conference adapts to available capacity
Material work SHALL receive independent product/completeness and architecture/verification challenge led by Codex, using separate agents when available and combined or sequential passes with honest receipts otherwise.

#### Scenario: Two reviewer slots are available
- **WHEN** the lead can delegate both complementary reviews
- **THEN** the reviewers inspect independently, exchange concise findings, and the lead resolves recorded disagreement from evidence

#### Scenario: Only one agent or provider is available
- **WHEN** concurrency or provider availability prevents delegation
- **THEN** the lead performs identified sequential role passes and continues without claiming model diversity

### Requirement: OpenSpec coverage is traceable and executable
Material hydrated outcomes SHALL compile into requirements with identifiers and observable scenarios plus dependency-ordered tasks naming owners, paths, acceptance criteria, and completion evidence.

#### Scenario: MCP catalog request
- **WHEN** a user requests an MCP catalog website
- **THEN** OpenSpec covers discovery, search, categories, details, ingestion, deduplication, updates, submissions, moderation, administration, installation guidance, operations, and an explicit per-MCP traceability inventory

### Requirement: Improvement rounds converge from refreshed evidence
After the requested outcome is delivered, the system SHALL rank and implement authorized qualifying improvements, refresh evidence, and stop only after two consecutive rounds yield no new qualifying winner or a precise blocker is recorded.

#### Scenario: First review finds no work
- **WHEN** one improvement review produces no qualifying candidate
- **THEN** the system refreshes applicable evidence and performs one additional review before convergence

#### Scenario: New evidence reveals a justified improvement
- **WHEN** a later round finds positive-value, reversible, verifiable work within authority
- **THEN** the system adds traceable requirements, implements and verifies the work, and resets the no-winner convergence count
