# F03 — Integration and contracts

Load this guide when the application profile or changed risk selects this family. Record applicability, priority, cheapest convincing layer, execution tier, pass/fail criteria, owner, and evidence. Combine scenarios when one independent test proves several obligations; not-applicable requires a product-specific rationale.

- **F03.01 — Worker runtime fidelity**: Worker runtime fidelity. Exercise real request handlers in the Cloudflare Workers test runtime using the repository's supported integration, exposing differences hidden by Node-only mocks and incompatible platform assumptions.
- **F03.02 — Database adapter boundaries**: Database adapter boundaries. Execute representative reads, writes, constraint failures, and transaction outcomes through real database adapters against isolated test databases, verifying actual query and serialization behavior.
- **F03.03 — KV consistency assumptions**: KV consistency assumptions. Test KV consumers against the application's declared stale-read and missing-value behavior; treat local emulator success as insufficient evidence of globally distributed consistency.
- **F03.04 — Object-storage contracts**: Object-storage contracts. Exercise R2 or equivalent storage adapters for content, metadata, checksums, missing objects, conditional updates, and streaming failures using the actual supported binding interface.
- **F03.05 — Durable Object interactions**: Durable Object interactions. Verify actual Durable Object routing, persisted state, alarms, and repeated requests where used, including lifecycle transitions that simplistic in-memory object fakes cannot represent.
- **F03.06 — Message producer-consumer contracts**: Message producer-consumer contracts. Connect real message serialization and consumer handling, checking schema versions, duplicate delivery, poison messages, and acknowledgement semantics under the platform's documented delivery guarantees.
- **F03.07 — Workflow step boundaries**: Workflow step boundaries. Verify durable workflow steps preserve required inputs, outputs, and resumable state across retries, using supported runtime tests and deployed checks for emulator capability gaps.
- **F03.08 — Service bindings**: Service bindings. Test requests across actual service bindings, verifying methods, paths, identity context, errors, and cancellation survive the boundary without depending on a fake local function call.
- **F03.09 — Request schema conformance**: Request schema conformance. Exercise required and optional fields, content types, unknown properties, and invalid encodings against executable API schemas, checking actual handler behavior matches published request contracts.
- **F03.10 — Response contract conformance**: Response contract conformance. Validate status codes, headers, body schemas, nullability, and error envelopes for successful and failed responses, including cases where an upstream dependency returns incomplete data.
- **F03.11 — Consumer-driven compatibility**: Consumer-driven compatibility. Add consumer-driven contracts for critical HTTP or message consumers and verify providers against relevant consumer versions; retain integration tests for runtime wiring beyond those contracts.
- **F03.12 — Version-skew scenarios**: Version-skew scenarios. Test old consumers with new providers and supported new consumers with old providers, focusing on field removal, enum expansion, defaults, and changed interpretation.
- **F03.13 — API specification drift**: API specification drift. Compare published API contracts with proposed changes and require targeted compatibility evidence for breaking classifications, including semantic changes that schema diffs alone cannot detect.
- **F03.14 — HTTP semantics**: HTTP semantics. Verify pagination links, redirects, conditional requests, caching headers, and content negotiation where applicable, testing clients and handlers together for the supported protocol behavior.
- **F03.15 — Webhook interchange**: Webhook interchange. Verify webhook payload serialization, exact-byte signature input, timestamps, event identifiers, and acknowledgement behavior with provider-compatible fixtures; cross-reference comprehensive attack cases to security testing.
- **F03.16 — Third-party fixture realism**: Third-party fixture realism. Maintain sanitized provider examples for deterministic adapter tests and validate their assumptions periodically against authorized sandboxes, detecting drift before fixture success becomes misleading.
- **F03.17 — Upstream failure protocols**: Upstream failure protocols. Exercise provider rate limits, Retry-After instructions, malformed responses, and transient errors through the real adapter, verifying bounded retries and meaningful failure translation.
- **F03.18 — Identity-provider interchange**: Identity-provider interchange. Verify supported identity-provider claims, callback parameters, issuer configuration, and token response formats with controlled integration environments; reserve exhaustive authorization abuse cases for security testing.
- **F03.19 — Multipart and streaming transport**: Multipart and streaming transport. Exercise multipart boundaries, binary payloads, streaming chunks, and interrupted uploads through actual parsers and transports, confirming content integrity and appropriate partial-failure handling.
- **F03.20 — Cancellation propagation**: Cancellation propagation. Abort clients during downstream work and verify cancellation reaches supported boundaries, releases resources, and leaves committed versus abandoned work consistent with the documented contract.
- **F03.21 — Proxy and routing context**: Proxy and routing context. Test forwarded host, scheme, path prefixes, and redirects through the application's real proxy configuration, ensuring generated links and routing decisions match deployed topology.
- **F03.22 — Middleware composition**: Middleware composition. Execute real routing and middleware chains for representative allowed and rejected requests, verifying middleware ordering produces the intended authentication, validation, and handler outcomes.
- **F03.23 — Tenant context propagation**: Tenant context propagation. Trace tenant context across handler, service, and storage boundaries using distinct fixtures, verifying the requested resource remains scoped correctly through joins and downstream requests.
- **F03.24 — Migration interoperability**: Migration interoperability. Exercise application reads and writes against supported schema transition states, including mixed application versions when rolling deployment can overlap database migration execution.
- **F03.25 — Search-index propagation**: Search-index propagation. Connect writes, index updates, queries, and deletion handling, asserting observable convergence within a declared deadline while distinguishing temporary indexing delay from permanently incorrect results.
- **F03.26 — Cache invalidation wiring**: Cache invalidation wiring. Populate real caches, perform relevant mutations, and verify subsequent reads follow the documented freshness policy, including invalidation events that cross service or tenant boundaries.
- **F03.27 — Notification transport contracts**: Notification transport contracts. Send composed notifications to a test sink through the real adapter, validating recipients, templates, links, headers, and provider rejection handling without delivering to unintended people.
- **F03.28 — Transaction-to-event consistency**: Transaction-to-event consistency. Verify committed changes produce intended events and failed transactions do not, exercising crash boundaries in the application's existing publication mechanism and downstream duplicate handling.
- **F03.29 — Cross-service cleanup**: Cross-service cleanup. Force failure after intermediate resources are created and verify compensation removes or marks them correctly, preserving evidence needed to resume legitimate partially completed work.
- **F03.30 — Worker storage isolation**: Worker storage isolation. Account for Workers integration storage isolation being per test file: explicitly reset per-test fixtures, distinguish namespaces, and verify cleanup before enabling concurrent stateful cases.

## Execution

Begin with critical existing behavior and the cheapest boundary that proves the invariant. Expand to runtime, browser, deployed, human, or deeper-audit evidence only when required. Missing dependencies or credentials are blocked evidence, never a pass.
