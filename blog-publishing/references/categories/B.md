# B — DATAFORSEO INTEGRATION

Load this category only when the article task, affected runtime boundary, or release risk selects it. The directives below are exact authorized requirements. Record applicability and live evidence in the adopting repository; policy presence is not runtime verification.

- **B01.** Implement a versioned, typed DataForSEO adapter with endpoint-specific request and response validation. Preserve provider fields and provenance, and consult current official documentation before changing parameters, pagination behavior, or supported endpoint combinations.
- **B02.** Keep DataForSEO Basic Authentication exclusively on trusted servers using protected configuration. Send the documented Authorization header over HTTPS; redact credentials from logs, browser bundles, job payloads, generated articles, analytics, and stored request snapshots. [S31]
- **B03.** Resolve supported location and language identifiers from provider metadata, and validate each endpoint independently. Do not add location or language fields to Search Intent requests, whose documented schema accepts keywords and an optional correlation tag. [S35]
- **B04.** Use a staged research funnel: generate fifteen researched editorial candidates, provisionally select the best eligible idea, research its seed, and use bounded comparisons if metrics justify reconsideration. Make budgets configurable instead of issuing maximum-depth requests for every idea.
- **B05.** Use Google Keyword Suggestions for phrases containing the topic seed, preserving the seed and returned query relationship. Request the intended location and language explicitly rather than relying on defaults that can widen or change the research market. [S32]
- **B06.** Use Google Keyword Ideas for category-based discovery beyond literal seed matches. Keep these results distinguishable from seed-containing suggestions so editorial reviewers can identify relevant adjacent opportunities and reject unrelated high-volume terms. [S33]
- **B07.** Use Google Related Keywords for bounded expansion through related-search relationships. Configure depth and result limits deliberately; the documented depth range is zero through four, with sharply increasing potential result counts at each level. [S34]
- **B08.** Batch supported keywords through Google Search Intent and retain main intent, secondary intents, and probabilities. Treat classifications as useful estimates; verify the selected article's intent against the observed results and the actual reader task. [S35]
- **B09.** Normalize metric names and meanings across endpoints. Label advertiser competition, CPC, bid estimates, organic keyword difficulty, and estimated traffic separately; never present advertising competition as a direct measurement of organic ranking difficulty. [S36, S37]
- **B10.** Retrieve available historical volume where seasonality affects selection, preserving every returned month and its coverage. Do not infer guaranteed earliest history from documentation examples, extrapolate missing months silently, or replace missing data with zero. [S52]
- **B11.** Use Bulk Keyword Difficulty for shortlisted terms when available, respecting its documented batch and locale requirements. Present its logarithmic zero-to-one-hundred score as a vendor estimate of organic difficulty, alongside the actual search-result context. [S37]
- **B12.** Make clickstream enrichment opt-in with explicit budget checks and field provenance. Where the documented flag doubles endpoint cost, reflect that multiplier before requesting it; distinguish modeled or normalized values from other search-volume fields. [S33, S38]
- **B13.** Obtain a sufficiently fresh Google organic SERP for the final target keyword using the documented advanced endpoint or asynchronous equivalent, allowing valid cached results within the SERP freshness policy. Preserve ranking URLs, observed features, retrieval time, and request context. [S41, S53]
- **B14.** Match SERP research to the intended location, language, and device, with documented defaults only when deliberately accepted. Record these settings beside results so desktop, mobile, and different-market observations are not compared as interchangeable measurements.
- **B15.** Compute SERP overlap locally from canonicalized ranking URLs to support keyword clustering. Use configurable thresholds and inspect intent before merging clusters; do not invent a dedicated provider endpoint or label overlap alone as proven cannibalization.
- **B16.** Persist an auditable chain from editorial idea to seed, expansions, scored candidates, selected target, and related terms. Store actual provider responses and decision rationale so a keyword choice can be reproduced and challenged.
- **B17.** Use Domain Intersection for relevant competitor-gap research when its domain-level perspective is useful. Preserve database update dates and returned ranking types; a competitor gap is an opportunity hypothesis, not proof that the site should publish. [S38, S54]
- **B18.** Enforce endpoint-specific batch sizes, limits, offsets, and continuation-token semantics. For example, Search Intent and Bulk Keyword Difficulty accept up to one thousand keywords; do not assume all endpoints accept identical batches or pagination fields. [S35, S37]
- **B19.** Preserve nulls, units, source fields, collection dates, database update dates, and market identifiers in normalized metrics. Display unavailable data as unavailable, and prevent stale observations from masquerading as current measured search demand.
- **B20.** Validate transport status, response-envelope status, and every task's status before accepting results. A successful HTTP response does not prove task success; retain useful error context without exposing authentication data or sensitive request contents. [S43]
- **B21.** Maintain a durable task ledger containing local request fingerprints, provider task IDs, status, costs, and result locations. Reconcile ambiguous paid POST outcomes before retrying; the provider's optional tag must not be treated as an idempotency guarantee.
- **B22.** Implement callback correlation and duplicate-event handling for asynchronous tasks. Prefer notification followed by an authenticated result fetch where suitable; do not claim provider-signed webhook verification unless the selected API explicitly documents that mechanism. [S39, S40, S53]
- **B23.** Enforce configurable endpoint-aware rate and concurrency limits with bounded backoff and jitter. Retry only appropriate transient conditions, stop on authentication or billing failures, and avoid replaying accepted tasks when polling or callback delivery fails.
- **B24.** Cache validated responses using canonical request parameters, endpoint version, market, and device where relevant. Give metrics and SERPs separate configurable freshness policies, refresh consequential stale data, and never cache failed responses as valid empty research.
- **B25.** Maintain a dated rate card and reserve estimated cost before requests; reconcile actual returned task costs afterward. Account for mode, priority, result depth, enrichment, and documented search-operator surcharges instead of applying one universal per-request price. [S39, S42]
- **B26.** Route suitable nonurgent SERP research through Standard asynchronous tasks and reserve Live calls for deadlines or interactive work. Track task completion through the documented lifecycle, respecting differences between polling, pingbacks, and result postbacks. [S39, S53]
- **B27.** Record costs, latency, cache hits, task failures, pagination, and useful returned candidates per article run. Use these operational metrics to reduce waste and diagnose missing research without pretending API expenditure predicts editorial quality or ranking success.
- **B28.** Persist required responses under our own retention policy. Standard results have documented thirty-day retention, with a documented exception retaining SERP Live JSON too; live-only Labs results need client storage. Verify endpoint-specific behavior and never treat provider retention as our backup. [S44]
- **B29.** Fail clearly when credentials, balance, supported locale, provider availability, or required keyword evidence is missing. Preserve the researched editorial draft and actionable error; never fabricate volumes, silently substitute another provider, or claim DataForSEO validation occurred.
- **B30.** Add focused contract tests and fixtures for schema changes, null metrics, pagination, task failures, duplicate callbacks, ambiguous submissions, and budget limits. Keep any paid live smoke test explicitly configured, bounded, and distinguishable from fixture-based verification.
