# AI Abundance — take everything 100 miles further

Cheap, abundant inference is the FLOOR under every build, not a line item to ration. This rule raises the ambition ceiling of `extra-mile`, `predictive-completeness`, `expand-context-always`, and the website-build-doctrine "AI-native spiral" (Phase 4).

## Core premise

- Inference is now cheap + abundant (DeepSeek Flash ~$0.14/M in · Pro ~$0.87/M out · Workers AI `env.AI` near-free tier). Treat the COST side of any AI enhancement as ~0.
- Invert the old "add AI only where essential / ration the calls" instinct. Default to MORE AI, not less.
- Every surface, feature, and interaction gets taken 100 miles further because an AI can power it at trivial marginal cost. The question is no longer "can we afford to?" — it's "why wouldn't we?"

## Operational (what this changes)

- When weighing an AI-powered enhancement, the cost side of the ledger is ~0. Ship it unless it harms UX, latency, or trust.
- Prefer generative / semantic / agentic over static: NL search > keyword filter · semantic rank > plain sort · generated per-item prose > blank/empty fields · chat-as-UI > rigid forms where natural · multimodal in > single text field · **AI-flow "next" > static sequential order**.
- **A "NEXT-ITEM" default (autoplay/up-next, an infinite feed, related/recommended, "what to read/watch/play next") is a PRIME, often-overlooked AI-upgrade target — flow by SIMILARITY via an existing recommendation engine instead of catalog/chronological order.** The core engagement loop of most media/content products is "what comes next," and it's usually dumb (catalog order, recency, round-robin). Upgrading it to flow by a grounded similarity/recommendation engine (one you likely ALREADY built for a "related items" surface — reuse it, ~free since it's cached) turns a disjointed sequence into a cohesive, endless, personalized-feeling experience = materially better retention. Ship it SAFE: opt-in (OFF by default = zero behavior change), **fail-soft to the old order** (any engine miss falls back, so it can never dead-end the core loop), respect explicitly-queued sequences (a user-built playlist/queue keeps its order), avoid immediate repeats (prefer a not-recently-seen pick so it keeps exploring), and make it visible + discoverable (a clear toggle; on mobile it can take a lower-value control's slot). Ref: bz.rocks 2026-10-25 — "AI Radio": free-play autoplay advanced in catalog order; a transport toggle now flows the next track to the current one's top `/api/similar` pick (reusing the cached "more like this" engine), fail-soft to catalog, mutually exclusive with shuffle → wake-up-alice flows to chef-lu-stew (its #1 similar). Cross-links `[[extra-mile]]`, `[[embarrassingly-easy-to-use]]`.
- Backfill every thin or empty surface with grounded AI content (liner notes, analyses, summaries, recommendations, per-item explanations) — never ship a blank field an AI could fill.
- **A thin, NEAR-IDENTICAL per-entity page is the #1 backfill target — and the cheapest fix is to REUSE an AI artifact you ALREADY generated for a sibling surface, not generate anew.** When a per-entity page (`/press/<id>`, `/product/<sku>`, `/profile/<id>`) is structurally rich but its CONTENT barely changes entity-to-entity (the only per-entity bits are a title + one field, the rest global/boilerplate), it reads as generic + under-delivers for that entity. Find the grounded AI content that differentiates it — and if a sibling surface already generates one (a liner note, a summary, an explanation, cached in KV), SURFACE THAT HERE rather than confining it to where it was first built (interconnectedness: AI output belongs on every surface where it adds value; cost ≈ 0, it's already cached). Fill it client-side via the existing endpoint (fail-soft, Trusted-Types-safe `textContent`), gate the section hidden-until-filled (no orphan heading). Ref: bz.rocks 2026-10-25 — every `/press/<id>` EPK was near-identical (global bio + a lyric excerpt the only per-track content); surfaced the track's existing `/api/liner` ("the story behind …", already built for the np-panel) as a "The story behind <title>" section → each kit is now genuinely track-specific with the editorial angle an editor wants. Cross-links [[extra-mile]], ai-permanence.
- **A per-entity field too HOMOGENEOUS to be a good grouping/recommender KEY can still be a GREAT per-item ENRICHMENT — if the generated line is grounded on a DIFFERENT sibling field that VARIES.** This is the COMPLEMENT of the dimension-variance gate ([[improvement-audit]]: a near-universal key is a useless feature driver → reject a recommender built on it). That gate rejects the field as a *grouping/recommending* KEY; it does NOT reject the field as an *enrichment ANCHOR*. A field that's intellectually central but shown as a bare disconnected value (a law/scripture/category/principle tag quoted but never tied to the item) is a prime backfill target: generate ONE grounded line connecting that value to a CONCRETE detail IN the item — never restating the value. The trap: if you ground the generation on the HOMOGENEOUS field itself, every line is interchangeable (the same clustering that killed it as a key). Ground instead on a sibling field that DIFFERENTIATES (lyrics, body text, specs, description) → concrete, item-specific output even though the anchor field clusters. Same anti-generic hygiene as every AI surface: BAD-examples-only prompt (no copyable GOOD, per the few-shot-parrot lesson), a deterministic `GENERIC` boundary backstop forbidding the interchangeable-platitude family, KV-cache, fail-soft, render it CONNECTED to the value it explains (not an orphan section). Ref: bz.rocks 2026-10-25 — each track's `wisdom` (a Robert Greene law / scripture) was a bare quote in the now-playing panel, never tied to the song; measured first = 168/168 have wisdom but only 17 laws group ≥2 (correctly did NOT build a wisdom recommender), then shipped `/api/wisdom` → ONE line tying the law to a concrete move IN the song, GROUNDED ON THE LYRICS (which vary), so output was concrete + 0-generic first pass (Matthew 5:8 "pure in heart" → "Bus full of saints with windows cracked, pure hearts navigating surreal landscapes."; Law 4 say-less → "CBO pen scribbles sparse, potent numbers."). Rendered under the quote with an accent rail so it reads as flowing FROM the law. Cross-links [[improvement-audit]], [[extra-mile]], [[frontend-judgeable-no-orphan-code]].
- Precompute + cache aggressively (KV / D1 / R2). Cheap inference means you can pre-generate per-track / per-page / per-item AI artifacts at build or first-request and serve them for days.
- Multiply, don't single-shot: ensembles, multiple personas/lenses, self-critique passes, re-rank — all affordable now.
- Re-prompting on a surface that "just works" is a prediction miss: assume the next pass should add an AI dimension the last one left on the table.

## Guardrails (cheap ≠ careless — all PRESERVED)

- Ground every generation to authorized real data. No invented people, facts, quotes, or stats. GROUNDED stays non-negotiable.
- Zod-validate AI outputs at the boundary, then convert to typed domain objects (Contract-First AI).
- Cache to protect latency and the free-tier rate limits; never let an AI call block first paint.
- Gate generation quality with evals where correctness matters. **Audit the actual OUTPUT, not just that the endpoint exists** — read real generations across several inputs; "the feature renders" ≠ "the feature is good". Generic, interchangeable prose (platitudes that could describe any item) is the #1 tell of a too-small model and/or a prompt that permits abstraction — fix by (a) the bigger model since it's cached (above), (b) a prompt that demands CONCRETE, item-specific grounding and forbids interchangeable abstractions — AND, crucially, name the axis that's generic and BAN it when it's constant across the whole set (if every item shares a trait, that trait is a NON-reason: "gospel-trap" can't explain why two gospel-trap tracks are similar), feeding the model richer per-item grounding (another field) so it has real hooks. (c) A DETERMINISTIC boundary backstop, because a prompt ALONE does not reliably hold on edge inputs — a tightly-clustered set makes the model repeat ONE theme verbatim across items. Over-generate (ask for N>k), then enforce the invariant in CODE at the boundary: reject the banned-axis phrasings, DEDUPE repeated reasons, and BACKFILL a duplicate from that item's OWN distinct field (grounded in real data, never invented) so you always return k distinct, specific, grounded results. Ref: bz.rocks 2026-10-24 — `/api/similar` shipped "Gospel-trap vibe" / "Epic gospel trap" as the *reason* two tracks matched (meaningless — all tracks are gospel-rap); fixed with forbid-genre + per-candidate `wisdom` grounding + request-5/dedupe/backfill-from-vibe → every track now returns 3 distinct concrete reasons ("Shared Bermuda location", "Mercy at the checkpoint"). **Ban the FAMILY, not the phrase, and give GOOD/BAD examples — the model DODGES a single banned string with a synonym.** When you forbid an exact phrase it substitutes a near-equivalent (ban "both tracks" → it emits "the two tracks"; the backstop regex + prompt ban must cover the whole family), and a positive example ("GOOD: 'Darkness shifts to neon skies'") steers far better than a prohibition alone. A code backstop that STRIPS a filler frame ("… links the two tracks" → kernel) then re-checks the remainder catches what the prompt misses. Always re-audit the live output AFTER the fix (the dodge only shows in the next generation). Ref: bz.rocks 2026-10-24 — `/api/segue` "Holy vibes bridge both tracks" → banned "both tracks", model switched to "the two tracks" → banned the family + GOOD/BAD examples + a strip-the-frame backstop → vivid fragments ("Steel transforms to mercy", "Crossing borders, prophecy to mercy"). **When the generic reasons CLUSTER, suspect the CANDIDATE POOL, not only the prompt — a recommender that returns near-duplicate VARIANTS (mixes/versions/editions/re-uploads) of ONE item has nothing distinct to say, so the reasons restate one trait N ways. Collapse variants to ONE representative in the candidate pool BEFORE ranking (+ exclude the query item's OWN variants); diverse candidates → genuinely distinct reasons, fixing the clustering at its root rather than papering over it in the prompt.** And **dedupe reasons with STOPWORD-STRIPPED prefix matching, never an exact/plain-prefix compare — semantic near-dups differ by an inserted filler word that defeats a literal match**: "Win through actions" vs "Win through YOUR actions never through argument" (both the same Law-9 wisdom) only collapse once "your/the/a/to…" are stripped, then one normalizes to a prefix of the other. Keep a flagged pick but RE-REASON it from that candidate's own grounding (wisdom→vibe), and prefer returning k-1 DISTINCT reasons over k with a near-dup/word-salad. Ref: bz.rocks 2026-10-25 — `/api/similar` returned 3 MIXES of one song reasoned "Shared awakening theme ×3"; fixed by collapsing base-song variants in the candidate pool + a stopword-stripped prefix dedup + forbidding the "X theme"/"reference" family (cache #v5→#v8) → every set is now 3 distinct, concrete, grounded reasons ("Noah builds before the flood", "Topple the throne in the shire"). **Banning a formula can surface an UNRELATED new crutch — not just a synonym dodge of the same concept — so budget for ≥2 verify→iterate rounds in ONE pass (re-read the output after EACH prompt change, not just once).** And for LONG-FORM output (an essay, a summary, a bio) the boundary backstop is REGENERATE-ONCE with a corrective system note (reject-to-null would throw away real content) — not the reject/backfill that fits a short caption/reason. Ref: bz.rocks 2026-10-25 — `/api/album-essay` banned "weaves a narrative of …"/"is a testament to …" (the interchangeable scaffolding in 40-47% of drafts) + a regenerate-once backstop → 0/14 framed; but the SAME verify pass caught the model's NEW opener crutch "X sets the tone" (11/14, an unrelated connective, not a synonym), fixed with one more soft nudge (#v4→#v6) → 0/14, every opener now unique + vivid ("Whispers of wonderland beckon in Wake Up, Alice", "Border Mercy dawns with checkpoint paperwork"). - **For a QUERY-DRIVEN recommender (NL/vibe SEARCH), a reason can be circular by ECHOING THE QUERY — not just by the genre/"matches the mood" template — and a PHRASE-PATTERN regex can't catch it; detect it by TOKEN-OVERLAP (reason's content words ⊆ query's) and BACKFILL from the item's own field.** A search `why` that merely re-labels the query ("late night prayer" → reason "Late night prayer"; "driving fast through the city" → "City driving") adds nothing — it's the circular non-reason the circular-regex family MISSES, because there's no template phrase to match, only the query's OWN words handed back. The fix mirrors the similar/segue pattern but keyed on the QUERY instead of a banned phrase: (1) the prompt demands a VIVID 5-10 word CONCRETE phrase that ADDS a detail the query lacks + BAD examples OF THE ECHO ('Late night prayer', 'City driving'); (2) a deterministic boundary backstop — tokenize both query + reason (lowercase, strip punctuation + stopwords), and if EVERY reason token is already a query token, BACKFILL the `why` from the item's OWN field (the track's `vibe`) rather than DROP a genuine match (a search result must keep its real match; only its weak reason is replaced). Guard it with a test asserting every reason adds ≥1 word beyond the query. Ref: bz.rocks 2026-10-25 — `/api/vibe` shipped terse echoes ('Late night prayer' / 'City driving'); added the echo BAD-examples + a token-overlap `isEcho` + vibe-backfill (#v3→#v4) → concrete reasons first pass ("Midnight rooftop supplication", "Trillion-interest debt-ceiling solo", "Dragon-slaying as self-rescue"; echo-cases backfilled to "Dawn-duffel chart-edge escape"). Cross-links `[[verify-against-source-of-truth]]`, `[[first-time-excellence]]`.
- **Probe a conversational/recommender AI with SPECIFIC REAL entities AND FAKE ones — hallucination hides behind generic prompts.** A vague question ("recommend a song") gets a plausible-sounding answer that may name a NON-EXISTENT item; asking about a SPECIFIC real entity reveals whether it answers about THAT one or riffs generically; asking about a FAKE entity reveals whether it invents details or honestly declines. The root fix is almost always the same: the authoritative data (catalog, inventory, docs) must be IN the model's context — a chat/recommender with no catalog in its system prompt WILL invent names + ignore specifics. Inject the real list + "recommend/discuss ONLY what's listed, never invent" (the grounded-retrieval pattern the search/vibe features already use); cheap inference makes the extra context free. Ref: bz.rocks 2026-10-24 — the DJ chat invented a song "Gold" + ignored the real album asked, until the full catalog was injected into its system context (then it recommended real tracks + rejected a fake "Diamond Rain"). **But grounding "injected" into a DEAD/never-taken CODE PATH is no grounding at all — verify it reaches the model on the LIVE path, not just that it exists in the source; the fake-entity probe is what catches a dead-branch injection, a code read does NOT.** The classic trap: the grounding is appended ONLY in a FALLBACK branch — `const system = body.system ? clientSystem : DEFAULT + catalog` — so when the client ALWAYS sends `body.system` (persona + live context, no catalog), the `else` with the catalog NEVER runs and the model is ungrounded, despite the catalog sitting right there in the code. Fix: ALWAYS append the critical grounding to WHATEVER base you use (`base = body.system ?? DEFAULT; system = base + GROUNDING + catalog`), never only to the default. Re-run the fake-entity probe AFTER the fix to confirm it's LIVE. Ref: bz.rocks 2026-10-25 — months after the "Gold" fix the 8B DJ STILL hallucinated a fake "Spiritual Warfare" because the catalog was only in the no-`body.system` fallback (the client always sends a system); moving the catalog to always-append → it recommended a real "Eisenhower Matrix from The Appeal" + declined "Diamond Rain Forever" ("couldn't find… from bZ's catalog"). - **A grounded recommendation is only HALF-delivered until it's ACTIONABLE — and a weak/fast model will NOT reliably emit the widget/tool-call SYNTAX, so back its PROSE with a DETERMINISTIC client-side entity-scan rather than trusting it to emit a directive.** A chat/recommender that renders a rich result widget (tap-to-play card, open-doc button, add-to-cart) ONLY when the model emits a special block (` ```aiwidgets ```, a tool call, a JSON fence) ships a DEAD-END SENTENCE whenever the small model answers in plain prose — the common case — so the user reads a real entity name but can't act on it (fails [[first-time-excellence]] § AI-native: "recommends → tap → it happens"). Backstop it CLIENT-SIDE: after the reply finishes AND only if the model emitted no explicit widget, scan the text for VERBATIM real-catalog entity names and auto-attach the actionable widget. Grounded (only real names match → never a hallucinated card), ZERO extra AI cost (pure string match against data you already have), fail-soft. False-positive guards are load-bearing: match LONGEST-first + boundary-delimited, CONSUME each matched name's text so a shorter name can't match a fragment of a longer one, and require short single-token names to clear a length bar (≥8 chars) so a common English word can't false-trigger a card. This is the actionability sibling of the deterministic-boundary-backstop family below (a prompt alone never reliably holds). Ref: bz.rocks 2026-10-25 — the DJ chat recommended real tracks in prose ("One Stop Higher from Panda Desiiignare") with no playable card; `detectTrackMentions()` now auto-cards verbatim catalog titles → tap-to-play in the persistent player (6 unit tests + a throttle-resilient prod E2E; live-verified card attached, 0 console errors). **Extending the backstop to a NEW entity type → RE-DERIVE the false-positive guard from THAT type's name distribution (measure the actual names first — don't reuse the previous type's guard), and order detection BROAD-ENTITY-FIRST so a container's children cover narrower mentions.** A guard tuned for one entity's names is wrong for another's: track titles needed "single-token ≥8 chars"; album names (all ≥2 words) instead needed "strip a leading 'the', then ≥2 words OR ≥9 chars" — because the real risk was common-phrase names ("The Appeal", "The Pause") that reduce to one ordinary word after "the". And detect the BROADER entity first (album → its full tracklist + a "play all" set), skipping per-child cards when it fires, so you don't double-surface a track the recommended album already contains. Ref: bz.rocks 2026-10-25 — `detectAlbumMentions()` added album-first (album-card + tracklist → "▶ Play all as a set", in-context), guard measured against all 15 album names → excludes exactly the 2 risky ones; "Start with Panda Desiiignare" now cards the album + 5 tracks + play-all (5 unit tests incl. the-appeal/the-pause, throttle-resilient E2E, live-verified). - **Turning AI-derived metadata (tags, categories, facets, auto-labels) into a tappable FILTER is a strong actionability win — but gate each value on SELECTIVITY, because a near-universal label is a USELESS filter that reads as a no-op (and a singleton returns only the item itself).** An AI that labels every item produces some values that describe ~EVERYTHING in the set and some that genuinely CHARACTERIZE an item — and only the latter make a meaningful filter. Expose all of them and tapping the universal one returns ~the whole catalog: the user taps and nothing meaningfully changes (fails [[embarrassingly-easy-to-use]] "never present a doomed/no-op control"). MEASURE the real frequency distribution against the LIVE data (not intuition — a domain's "obvious" headline tag is often the least selective) and only make a value explorable when it PARTITIONS the set — e.g. `2 ≤ count ≤ ~45%` of the corpus. Reuse the existing membership index to resolve co-tagged items (don't re-run AI — the classification is already computed; serving it as navigation is ~free, the precompute-and-serve pattern). Corollary (DISPLAY, not just filter): the near-universal labels are also the LEAST informative to SHOW — a label ~every item shares is background, not identity; the rare ones characterize the item, so RANK the displayed labels by distinctiveness (SELECTIVE-first, then rarest — TF-IDF), pooling namespaces + deduping, so the surface both reads as item-specific AND leads with the tappable ones. QUANTIFY a label-selection's quality by its COVERAGE GAP — how many items get 0 characterizing/selective labels under it — and compare before/after against the live data, don't eyeball it. Ref: bz.rocks 2026-10-25 — (a) made SELECTIVE hero chips (`tagExplorable`: 2 ≤ freq ≤ 45% of 168) tappable `<button>`s filtering to co-tagged tracks via the already-built-but-unused `tracksByTag` (bay-area 9 → a focused 7-track result), while near-universal moods (sacred 92%, gospel 85%) stay inert — tapping one would've returned 155 (≈everything); (b) the FIRST selection (first-2-moods + first-of-each) left **66/168 tracks (39%) with 0 explorable chip** — the affordance was invisible on 39% of the catalog; ranking the pooled namespaces SELECTIVE-first/rarest-first dropped that to **4** and made the chips characterize the track (chef-lu-stew SACRED/MERCY/GOSPEL → NO-SUBSTANCE/BAY-AREA/SAINT-JOHNS/PLACE-NAMED/FOLK; bermuda-slipstream leads with `bermuda`). - **Upgrading to a stronger model can EXPOSE prompt-leak bugs an 8B glossed over** — a bigger model more readily echoes an ALL-CAPS imperative phrase as if it were content (e.g. a prompt opening "GROUNDED ONLY in <X>…" surfaced verbatim as the essay's first words). Prefer VERB-phrase instructions that can't read as prose ("drawing ONLY on <X>", "base it strictly on <X>") over noun-phrase imperatives, add "output only the <thing> — never restate these instructions", AND keep a cheap suppress-on-leak guard at the boundary (`if (/\b(instruction phrase)\b/i.test(out)) out=''` → fail-soft to hidden). Re-verify output after ANY model swap. Ref: bz.rocks 2026-10-24 — 8B→70B on liner/meaning/segue/album-essay/similar; the album-essay leaked "GROUNDED ONLY in" until rephrased + guarded. **Keep that guard's regex to UNAMBIGUOUS instruction phrases ONLY — never list natural domain/artist vocabulary that legitimately appears in good output, or the guard silently drops valid generations (a false-positive that reads as "the AI returned nothing").** Ref: bz.rocks 2026-10-24 — a share-caption leak-guard that listed "gospel-rap" / "Newark hustle-gospel" (the artist's OWN genre words, which belong in a caption) would have suppressed perfectly good captions; narrowed to the instruction phrases ("drawing only on", "output only the", "interpret only what", "never invent"). **The same echo-as-content trap hits VOICE/TONE descriptors — a model lifts the prompt's STYLE ADJECTIVES verbatim as the output's content, and the result is generic copy that fits every item.** "Voice: hard, holy, vivid" → the model opens with "Hard holy vibes" on ~every track (a phrase that says nothing in a catalog where every song is holy). Fix at THREE layers: (1) phrase voice guidance so its words can't BE the content — describe the REGISTER in terms you'd never want echoed ("street-smart, faith-rooted, cinematic") rather than handing the model usable words ("hard, holy"); (2) demand the output LEAD with the item's OWN concrete specific (its image/story/line) + forbid the resulting generic FAMILY with BAD/GOOD examples; (3) a deterministic boundary backstop that, when the generic formula still appears, BACKFILLS from the item's own grounded field (a vivid lyric line, the album tagline). Bump the cache key so stale generics regenerate. Ref: bz.rocks 2026-10-25 — `/api/sharecopy` emitted "Hard/Holy vibes X" on 4/6 tracks because the "hard, holy" voice was parroted; reframed the voice + forbade "(hard) holy/gospel vibes/beats" + a `GENERIC_CAP` lyric-backfill (#v1→#v2) → 0/8 generic, all concrete ("One point nine in the deficit hole 💸", "Mikewell on the platform, cane taps the floor 🚶"), guarded by a prod E2E. **And the trap's THIRD form: FEW-SHOT EXAMPLES get copied VERBATIM — the model reuses a "GOOD:" example's exact wording/opener as the answer, often UNGROUNDED, and it ONLY surfaces across MANY samples (one output looks fine → read ≥6 before trusting a few-shot prompt).** Keep examples few + structurally diverse, label them "STYLE ONLY — never reuse their words or opener; build from THIS input", ban the specific copied opener, and backstop verbatim reuse → fail-soft. - Never fake an AI capability in the UI. No selector/toggle that claims a model (or tier) it doesn't actually use — label the real model. An honest "Llama fast / Llama deep" beats a fake "Claude Opus". **An honest UI is necessary but NOT sufficient — the SERVER must back it:** the endpoint ALLOWLISTS the real values and IGNORES anything else (→ its real default), and the response ECHOES the model ACTUALLY used (track the fallback — a 70B→8B degrade echoes 8B), never the value the client requested. Without the allowlist a bogus/stale/injected `model` passes straight to `env.AI.run()`, errors, silently falls back to the small model, and the response mislabels it as whatever was asked — a fake capability even when the UI code looks right. Generalizes to any capability selector (model · tier · quality · voice · provider): reject-or-default server-side + echo-what-ran. Ref: bz.rocks 2026-10-24 — the DJ chat offered Claude Haiku/Sonnet/Opus options (none exist on Workers AI → every one silently ran Llama 8B while the API echoed the requested `claude-*` string, and even `totally-fake-model-xyz-999` was accepted); fixed with a `CHAT_MODELS` allowlist + `usedModel` echo + honest `Llama 8B/70B` options + a localStorage coercion guard for stale stored values.
- **A surface LABELED "AI" that's actually a DETERMINISTIC formula (popularity sort, rules-engine, static grouping) is the same fake-capability class — but the AI-abundance fix is to make it GENUINELY AI (upgrade), NOT to relabel it honestly (downgrade).** Honest relabeling ("Popular" instead of "AI") is the floor; when you already have a cheap GROUNDED AI engine in the product, the directive ("take it 100 miles further, AI powers everything") says USE it — turn the fake-AI surface into real AI. And prefer **context-aware over a global chart duplicated across surfaces**: a per-user/per-session surface (a queue, a "for you", a next-up) showing the SAME global ranking as a homepage chart both mislabels AND wastes the personalization the surface exists for — seed it from the user's current context (what they're playing/viewing) via the grounded engine, with the AI's REASON surfaced (the "why"), popularity as honest fill, instant-paint + async-upgrade + fail-soft so it never blocks or empties. Ref: bz.rocks 2026-10-25 — the Queue "AI" tab (✦) was `aiPicks()` = global `plays×0.73+shares×0.27`, identical for everyone + duplicating the homepage Aeon rail; rebuilt to lead with grounded "✦ Because you're playing <X>" picks + their `why` from the already-cached `/api/similar` (70B, KV-cached), then "Popular now" fill — genuine contextual AI, reusing a proven endpoint (no new model cost), fail-soft to popularity. **Sibling-sweep corollary:** after upgrading ONE recommender to the grounded engine, AUDIT EVERY sibling "related / next / more-like-this / up-next" surface — one often silently stays on a local heuristic (drift), so the product's "more like this" story is inconsistently grounded. Reuse the SAME engine (share its KV-warmed cache → zero duplicate fetches), surface the same `why`, and keep instant-local-paint → async-upgrade → fail-soft + a current-item race-guard.
