# Verify Against Source of Truth (Data Reconciliation)

Render-integrity verification is BLIND to wrong-data. A surface that loads cleanly — 200, 0 console errors, 0 failed requests, axe-clean, a screenshot that looks fine — can still display the WRONG data (an empty state while real records exist, or a stale/different count). Every prior check only proved *"the UI renders what its endpoint returns"* — never *"the endpoint returns what the AUTHORITATIVE STORE actually contains."* Close that gap: reconcile display-vs-store, not just render-vs-endpoint.

## The blind spot (how the class slips through)

- **Empty renders cleanly.** "No traffic yet" / "0 results" / "not available" passes EVERY render-integrity gate. A screenshot of an honest-looking empty state scores fine on AI-vision. Nothing distinguishes *honestly-empty* (0 real records) from *lying-empty* (records exist, UI reads the wrong source).
- **Single-source verification is self-referential.** Checking "does the UI show what the endpoint returns" never asks "does the STORE contain records the UI should be showing but isn't." A wrong-source bug is a mismatch between the write-store and the read-source — structurally invisible to a one-source check.
- **200 + empty reads as "working."** A `200 {items:[]}` from the WRONG endpoint isn't broken — it's the wrong endpoint. All the health gates stay green.
- **Reference incident (projectsites, 2026-08-06):** `/admin/analytics` showed "never had any traffic" for a site with **109 real pageviews** in D1 `visitor_events` — the UI read CF-zone `httpRequestsAdaptiveGroups`-per-host (empty for `*.projectsites.dev` subdomains). Survived ~30 render-integrity fires; a prior memory even concluded the empty was "honest 0-traffic." Only a human with ground truth ("I just visited it") caught it.

## The discipline — reconcile every data surface

For every surface that DISPLAYS stored data, verification MUST cross-check two independent things:

1. **Ground truth** — query the AUTHORITATIVE STORE directly (D1 table / Tinybird / R2 / Stripe) for the real account: does it have records for this concept? (`SELECT COUNT(*) … WHERE org_id = <real user>`).
2. **Display** — call the surface's endpoint AS THE REAL USER (real session, real browser if the API is bot-challenged) and extract what it shows.
3. **Flag divergence** — `groundTruth > 0 && display == 0` → **LYING-EMPTY**. `groundTruth != display` (counts differ) → **WRONG-SOURCE / STALE**. `groundTruth == 0 && display == 0` → honest-empty (fine).

A surface is "verified populated" ONLY when its display reconciles with its store — never on render-integrity alone.

## The causal test (strongest finder for "I did X, it's not shown")

For trackable surfaces (pageviews, submissions, events, orders): perform the action → assert the STORE records it → assert the DISPLAY surfaces it. This catches the exact "I visited the site and it says no traffic" class that static reconciliation of a quiet account can miss.

## Build the reconciler as a reusable tool, not a one-off

- A ground-truth data sweep (`SELECT COUNT(*)` per concept for the real account) is the objective "which surfaces MUST show data" map — run it FIRST; it tells you where to look.
- A display reconciler logs in as the real user (in a real browser when the API 403s headless bot calls — `page.evaluate(fetch + Bearer)`), hits each surface, and diffs against ground truth.
- Reference impl: projectsites `e2e/admin-verify/reconcile-surfaces.mjs` — reconciled 9 admin data surfaces; found analytics was the sole divergence (7 others clean). Keep it and re-run each verification pass.

## Anti-patterns

- Concluding an empty state is "honest 0-traffic / correct empty" from the SAME source the UI reads — always confirm against the authoritative store.
- Marking a section "verified, populated" on a green render + a screenshot, without a ground-truth count behind it.
- Trusting a `200` as "the data is right" — a wrong-source endpoint returns 200.
- Verifying with a test-org account that has no data (everything honestly-empty → nothing to reconcile) when the real user's account is where the data + the bug live.
- **Asserting "published on npm/JSR/PyPI/crates" from the presence of config, not the registry.** A `package.json` / `jsr.json` / `pyproject.toml` in the repo means it's CONFIGURED to publish, NOT that it IS published. The authoritative store for a distribution claim is the REGISTRY — `curl registry.npmjs.org/<pkg>` / `jsr.io/@scope/name` (404 = not published). Ref: agent.megabyte.space 2026-10-06 — the FAQ claimed "published on npm, JSR, and GitHub" but both npm and JSR 404'd (only GitHub was real); the repo's package.json + jsr.json made it LOOK published. Same for any "available at / live at / deployed to" claim — hit the actual endpoint.
- **The upstream "source of truth" can itself be STALE/inconsistent for an EXTERNAL fact (a model version, a product release) — web-verify, and a downstream showcase can be correctly AHEAD; don't align it DOWN to the stale majority.** When a repo is mid-migration the same external fact appears in two versions at once (e.g. 23 "Ideogram v3" refs vs 13 "Ideogram 4.0", even within one skill). For a FACTUAL external claim the ultimate authority is REALITY (a web check), NOT the repo — confirm the current value before "fixing" anything (Ideogram 4.0 shipped 2026-06-03, verified; v3 is the retired March-2025 model). A showcase already using the newer value is RIGHT; aligning it to the repo's stale majority would REGRESS it. Guard the verified-current value with a test + rationale so a later pass can't naively correct it down. (Sibling of the published-vs-configured bullet above: the repo is not the ultimate authority for EXTERNAL facts.) Cross-links `[[prompt-as-training-signal]]`.
- **A public CLAIM can be faithful to the internal DOCTRINE yet inapplicable to the actual OUTPUT — verify claims against the shipped STACK, not just whether the term appears in the docs.** A legacy/vestigial gate term survives in the doctrine (a WordPress-era SEO metric, a retired tool, an old framework version) and then surfaces on a showcase describing output that CANNOT use that technology — misleading even though it's "traceable to the rules." The authoritative check for a product claim is the actual output stack: does what we SHIP actually support/produce this? The lone-outlier term is the tell — the same concept is framed differently everywhere else. Ref: agent.megabyte.space 2026-10-07 — the Before/After compare claimed "Yoast green" (a WordPress-only plugin) one line below "CF Workers + Angular + D1"; the agent produces no WordPress, so Yoast can't apply, and it was the only "Yoast" on a site that frames SEO as JSON-LD/GEO everywhere else — replaced with the stack-appropriate "SEO + JSON-LD." When auditing showcase/marketing claims, cross-check each against the real stack AND how the SAME concept reads elsewhere on the surface. Cross-links `[[drift-detection]]`.
- **Updating a fact on one surface while sibling surfaces show it stale.** The same fact (a count, a stack choice, a list length) is usually duplicated across hero / capabilities / a dedicated section / section-heading / `llms.txt` / FAQ / `<meta>`. Updating one and missing the others leaves stale duplicates that still read as authoritative. When you change a displayed fact, `grep` its OLD value across the WHOLE site and update every occurrence; better, add a cross-surface **consistency test** (per-card counts must sum to the headline; a section must not show a retired/banned tool). Ref: agent.megabyte.space 2026-10-06 — three separate fires each found a fact current in capabilities/`llms.txt` but STALE in its dedicated section (platforms heading 37 vs 34 listed; per-card doc badges summed to 109 vs 149 headline; stack section still showing PrimeNG/Resend/Angular 21). Cross-links `[[drift-detection]]`, `[[prompt-as-training-signal]]` §4.
- **"Correcting" a canonical derived stat to a naive recount.** A self-reported count may use a PRECISE definition — reproduce that definition (try `-maxdepth`, file-type/name exclusions, etc. until your count matches the canonical number) BEFORE "fixing" it; a different-metric recount is not a correction. Then fix only what genuinely drifted — e.g. a stale per-item breakdown that must sum to the canonical total. Ref: agent.megabyte.space showcase 2026-10-06 — nearly changed "149 reference docs" → 153 across ~12 surfaces before `-maxdepth 1` reproduced 149 (nested subdir docs in 2 categories are excluded); the headline was right, only the per-card breakdown (summed to 109) was stale. Cross-links `[[prompt-as-training-signal]]` §4.
- **A green count/consistency GUARD ≠ the surface is accurate — guards check COUNTS, not COVERAGE.** An automated accuracy guard (e.g. "decks ↔ API ↔ hero all agree on 23/28/149/37") enforces numeric consistency, so it stays green while a NEW capability the source system gained is silently absent from the prose, or while a term the source doctrine moved on from is still the only framing shown. Counts don't drift; *coverage* and *framing* do — invisibly. When the upstream source adds a capability or shifts terminology/approach, `grep` the showcase for the OLD framing and add the new one; don't trust "the guard is green" as "the description is complete + current." Ref: agent.megabyte.space 2026-10-07 — the build's 23/28/149/37 guard was green for many fires while the site framed retrieval only as "Vectorize RAG" and never named **AI Search** (the managed layer the agent-fabric work added in skill 28); a by-name audit against the upstream submodule surfaced it. Cross-links `[[drift-detection]]`, `[[prompt-as-training-signal]]` §4.
- **When the upstream OWNS a count/claim in a dedicated SoT file, guard the showcase against THAT file — not an internal transcription of it.** A repo that maintains a manifest declaring "update the N claim via this file ONLY" (e.g. `platforms.json` with `variants.length`) has made that file the single source. Transcribing the number into downstream code (a hardcoded `/api` count, a hero stat) creates a SECOND source; a guard that only checks `transcription == transcription` (site tags == hardcoded API count) stays green while BOTH silently drift from the manifest. The guard must read the owning file. Ref: agent.megabyte.space 2026-10-07 — the build verified site-platform-tags == `/api/skills` (both 37, internally consistent) but never read the upstream `platforms.json` SoT; added a cross-check (site + `/api/skills` == `platforms.json` `variants.length`, mirroring the existing per-card-doc-count + agent-tier cross-checks) so an upstream add/remove/rename can't drift silently. Cross-links `[[drift-detection]]`.
- **A showcase's HEADLINE/summary list can omit a flagship capability that exists only DEEP in a detail deck — audit summary-vs-detail, not just the count.** The scannable "what it does" list (feature grid / capabilities cards) is where a visitor judges the product; a capability buried as one card inside a big deck (e.g. 1 of 28 agents) reads as *absent* from the headline even though it's technically "on the site." A count guard (N features, M cards) stays green while the summary under-sells. When auditing completeness, diff the SUMMARY list against BOTH (a) the site's own detailed decks and (b) the upstream source DESCRIPTIONS (not just counts) — then ELEVATE flagship capabilities into the summary and add an E2E asserting they appear THERE specifically (not only in the deep deck). Ref: agent.megabyte.space 2026-10-07 — the Sentry→agent→auto-PR "self-healing" incident-remediation pipeline + Sentry error-tracking (both prominent in upstream skill 13) lived only in the deep agents deck, absent from the "main features" capabilities list; surfaced both as headline bullets + guarded. Cross-links `[[drift-detection]]`, `[[prompt-as-training-signal]]` §4.
- **A curated "stack/tech showcase" omits the FOUNDATION (language, runtime) as "assumed" — and a DIFFERENT audit modality is often what surfaces it.** The flashy differentiators get listed; the most fundamental layer (the language itself) is taken as given and left off. Two compounding lessons: (1) auditing a "what we use" list for completeness, explicitly confirm the FOUNDATION is shown, not only the differentiators; (2) alternate audit MODALITIES — a VISUAL pass catches what a CONTENT pass misses and vice versa: an unbalanced layout can be the tell for a missing item. Ref: agent.megabyte.space 2026-10-07 — 24 content-accuracy passes never caught that "Built for the Modern Stack" showed NO language; the first visual audit flagged a lone-card grid imbalance, and fixing it meant adding the genuinely-missing "TypeScript 7 · oxlint · lefthook" category — the foundation AND the imbalance fix were the same edit. Cross-links `[[drift-detection]]`.
- **`<head>` is a STRUCTURAL blind spot for every visual / AI-vision audit — it is never rendered.** Meta description, `og:`/`twitter:` tags, JSON-LD, canonical, `<title>` carry counts, framing, and URLs that screenshots and vision-QA can NEVER see — so a "gorgeous, every component" visual pass (even a Hard-Gate AI-vision one) structurally cannot catch a stale `<head>`. Always pair a visual pass with a SOURCE-level `<head>` check (counts, framing, canonical/OG URLs), and guard the duplicated counts at build time. Ref: agent.megabyte.space 2026-10-07 — a full desktop+mobile visual audit was clean, but a `<head>` check found the `og:`/`twitter:`/meta descriptions carried the 23/28/149/37 counts on an UN-guarded surface (same class as the manifest "19-category" rot) — now build-cross-checked against the decks. Cross-links `[[drift-detection]]`.
- **Headless Chromium does NOT composite `backdrop-filter` (+ some GPU effects) — a glass/blurred overlay screenshots as false BLEED-THROUGH; verify computationally, don't "fix" a non-bug.** A `backdrop-filter: blur()` + near-opaque `rgba()` menu/modal looks transparent (content showing through) in a headless screenshot even when the CSS + stacking are perfectly correct. Before changing anything, confirm with code: `getComputedStyle` shows the backdrop IS applied (`rgba(…,0.95)` + `blur(16px)`), and `document.elementFromPoint(x,y)` on the panel returns the OVERLAY as the top-painted element (so it stacks above content). Ref: agent.megabyte.space 2026-10-07 — the open mobile-menu screenshot showed the hero bleeding through; computed backdrop present + `elementFromPoint`=the panel + the menu living in a `position:fixed; z-index:100` nav confirmed it's gorgeous in real browsers (pure headless artifact). Complements the `<head>`-blind-spot above: a screenshot/vision pass both MISSES `<head>` and MISRENDERS GPU effects. Cross-links `[[drift-detection]]`.
- **A hardcoded DATE/timestamp in a served file is drift BY DESIGN — derive it from the build, don't hardcode it.** A `sitemap.xml` `<lastmod>`, a "last updated" footer, a copyright year, a cache-version string: any time-sensitive value written as a literal will silently rot as the real artifact changes around it. A stale `lastmod` is worse than none — it actively tells crawlers "nothing changed since <old date>," so heavily-updated content gets under-recrawled/under-indexed. **Fix the root cause, not the value:** have the build step rewrite it (for a deploy-driven static site, the deploy date IS the last-updated date — regenerate every `<lastmod>` to the build date on each run; idempotent within a day). Ref: agent.megabyte.space 2026-10-07 — both sitemap URLs sat at `<lastmod>2026-04-24</lastmod>` ~6 months after dozens of deploys; moved the date into `gen-llms-full.mjs` (which already auto-generates `llms-full.txt` + guards counts) so it can't rot again, and added an E2E asserting every sitemap `<loc>` resolves 200 (a sitemap entry that 404s is a real SEO defect) with a current-era `<lastmod>`. Same purge caveat as any non-cache-busted asset (below). Cross-links `[[drift-detection]]`.
- **A prod `200` can serve STALE CACHED content after a successful deploy — the origin is fixed but the edge still serves the old bytes.** For a static asset WITHOUT a cache-busting query (`manifest.json`, `robots.txt`, `sitemap.xml`, `og.png`, `/`), a `max-age` cache means `wrangler deploy` updates the origin but the edge keeps serving the cached version until TTL expiry (`cf-cache-status: HIT`). Verifying the plain URL shows the OLD content and reads as "deploy didn't work." **Diagnose:** fetch with a cache-buster (`?cb=<ts>`) — if that shows the NEW content, the origin is fixed and it's a CACHE-stale problem (purge it); if it ALSO shows old, the deploy genuinely failed. **Fix:** purge the asset (`POST /zones/{id}/purge_cache {"files":[url]}`) — the deploy mandate's "CDN purge paired" exists for exactly this — then re-verify the plain URL. Cache-busted assets (`styles.css?v=…`) don't need this (the new URL misses the cache). Ref: agent.megabyte.space 2026-10-07 — fixed `manifest.json`'s stale "19-category", deployed, but the plain URL still showed "19" (`HIT`, `max-age=86400`) while `?cb=` showed "23"; a purge made it live. Cross-links `[[verification-loop]]`.
