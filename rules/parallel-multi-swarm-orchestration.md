# Hyper-Saturated Prompt Hydration, Right-Sized SCRUM Synthesis & Multi-Swarm Parallel Orchestration (`Claude` · `Codex` · `Gemini` · `OpenCode` DeepSeek)

Every material prompt entered into a supported harness triggers a deterministic convergence pipeline. The pipeline expands context and implementation aggressively while preserving the user's authority ceiling: deployment, publication, paid services, credentials, destructive actions, and external communications require the authority that governs those actions. Coverage and production claims are evidence, never fixed slogans.

---

## 1. What Happens First When a Prompt Is Entered (The 7-Stage Automatic Hydration Pipeline)

### Stage 1 — `UserPromptSubmit` Hook Interception & Unified Skill + Context Hydration

1. The moment a prompt is submitted, `hooks/hooks.json` and `~/.claude/settings.json` invoke `bin/prompt-hydration-hook.mjs`, which executes `bin/prompt-hydrator.ts` and `bin/skill-router.py` before the primary agent takes its first tool action.
2. The hydrator preserves the user's verbatim request as the delivery floor, redacts secrets from diagnostic logs, hashes governing instruction files (`AGENTS.md`, `CLAUDE.md`, `CODEX.md`, `GEMINI.md`), and resolves active `openspec/changes/*` deltas.

### Stage 2 — Mandatory Product & Architecture Gap Audit (e.g., Unfinished `"Settings"`, Missing `@theme.tools/*`, Missing Plugin Catalogs)

1. For material product work, `bin/prompt-hydrator.ts` runs `auditProductGaps(checkout, prompt)` across relevant repository surfaces. Focused fixes remain focused unless verified evidence shows an adjacent defect is required for the requested outcome.
2. If any standard application capability is missing, stubbed, or incomplete — such as **Settings & Preferences**, **Authentication & RBAC**, **Billing & Usage Metering**, **Notifications & Inbox**, **Onboarding & First-Run**, **Admin & Audit Log**, **Extensible Plugin Catalog**, **28 Canonical `@theme.tools/*` Thin-Shell Bindings**, **Cloudflare Worker/Domain Config**, **100% Unit Test Coverage**, or **Cloudflare Browser Run Parallel E2E Specs** — the audit automatically injects remediation tasks into `inferredRequirements` and the OpenSpec backlog.
3. The system delivers **what the product and user need to succeed**, not merely the literal minimum nouns in the prompt (`[[intent-complete-delivery]]`, `[[feature-expansion-mandate]]`).

### Stage 3 — Architect Categorical Cycling, Heavy Web Research, Competitor Analysis & Full Plugin Catalogs

1. For every feature or application request, the **Frontier Architect** (`agents/architect.md` running on `claude`, `codex`, or `gemini`) cycles through **all 10 categorical dimensions** of the application:
   - `C01` Core Domain Workflows & State Machines
   - `C02` Account, Workspace & Multi-Tier Settings (`Settings` Completeness Gate)
   - `C03` Extensible Plugin & Integration Catalog (Massive Parallel Swarm Default)
   - `C04` `@theme.tools/*` 28-Library Thin-Shell Composition & 16-State OKLCH UI Craft
   - `C05` AI-Native Automation, Copilots & Edge Inference
   - `C06` Security, RBAC, Tenancy, CSP Level 3 & Trusted Types
   - `C07` Data Lifecycle, Drizzle Migrations, Import/Export & Backup Recovery
   - `C08` Billing, Entitlements, Cost Controls & FinOps Telemetry
   - `C09` SEO, GEO, JSON-LD, Accessibility (WCAG 2.2 AA) & i18n
   - `C10` Production Delivery, Cloudflare Bindings, Domain Routing & Parallel Browser Run Verification
2. Across each applicable category, the Architect executes parallel primary-source research and competitor/substitute tear-downs. Findings enter scope only after evidence, authority, confidence (`>=0.8`), net-value, compatibility, and verification filters. Repeat after implementation until two refreshed rounds produce no new qualifying winner.
3. Whenever a feature or product supports extensibility (plugins, connectors, blocks, exporters, themes, rules, widgets), the Architect designs a **full plugin catalog by default** and shards its implementation across a massive parallel `opencode` (DeepSeek) worker swarm.

### Stage 4 — Right-Sized Collaborative SCRUM Deliberation Quorum (`bin/scrum-deliberation-quorum.ts`)

1. For all important architectural, product, UX, or security decision-making, further instructions are dictated by the contextual synthesis of a **collaborative SCRUM-style meeting** (`bin/scrum-deliberation-quorum.ts`) convened with **only the specialist agents that need to be there**.
2. The quorum selector maps the prompt's active domains to the minimum required specialists (typically 3–6 agents from the 28-agent roster, e.g., `architect`, `product-manager`, `ui-designer`, `appsec`, `database-engineer`, `qa-verification`), excluding unrelated specialists to prevent token bloat.
3. Quorum members run across heterogeneous frontier models (`claude`, `codex`, `gemini`) in parallel, challenge each other's assumptions, and emit a **Synthesized SCRUM Blueprint + Dissent Register + Locked Interface Contracts**.

### Stage 5 — Frontier Architect OpenSpec DAG Generation & Documentation Self-Improvement

1. The assigned Frontier Architect (Claude by default; Codex or another repository-eligible frontier harness when explicitly assigned; **NEVER `opencode`**) consumes a decision-ready hydrated brief and SCRUM synthesis to create or update complete **OpenSpec** artifacts. Codex coordinates system operations and Paperclip where available and authorized; Gemini handles long-context, market/competitor, and multimodal review; OpenCode performs bounded work only after contracts are locked.
2. Every task in `tasks.md` and `task-graph.json` is decomposed into an atomic, parallel-safe DAG node with disjoint file ownership (`ownedFiles`), explicit dependencies (`dependsOn`), model tier assignment (`frontier-claude` | `frontier-codex` | `frontier-gemini` | `throughput-opencode-deepseek`), and machine-verifiable acceptance criteria.
3. Simultaneously, the Architect and a parallel documentation swarm iteratively audit and upgrade `README.md`, `AGENTS.md`, `CLAUDE.md`, architecture docs, and inline JSDoc/TSDoc comments with web-researched domain precision.

### Stage 6 — Massive Multi-Swarm Parallel Implementation (`Claude` + `Codex` + `Gemini` + `OpenCode` DeepSeek Offload)

At intake and after each dependency clears, dispatch independent work concurrently whenever doing so reduces time to verified delivery. Delegate every suitable task to OpenCode with DeepSeek through LiteLLM when it meets the acceptance bar and improves throughput. Use Codex, Gemini, or Claude for work that benefits materially from premium capability or independent review, and record concrete reasons for premium routing or limited dispatch. Scale worker count to ready work, isolation, and approved capacity.

1. The host-configured `bin/evidence-gated-orchestrator.ts` executes the verified OpenSpec DAG through approved scheduler adapters across isolated Git worktrees. The legacy `bin/multi-swarm-orchestrator.ts` compiles planning examples only.
2. **80%+ OpenCode (DeepSeek) Offload Mandate**: Every `throughput-safe` DAG task (feature shards with locked contracts, full plugin catalogs, UI components across all 16 states, 100% unit tests, Playwright E2E specs, Drizzle migrations, docs) is offloaded to parallel **`opencode` swarms powered by DeepSeek** (`litellm/deepseek-v4-pro` and `litellm/deepseek-flash` via `https://llm.megabyte.space/v1` and `bin/opencode-deepseek.sh`), preserving premium `claude`, `codex`, and `gemini` subscription quota.
3. **Parallel Frontier Triad Swarms (`Claude` + `Codex` + `Gemini`)**: When frontier cognition is required, `claude`, `codex`, and `gemini` run in parallel on distinct architectural shards, speculative critical-path races, or cross-model adversarial reviews.

### Stage 7 — Proportionate Coverage, Parallel Browser Verification & Authorized Delivery

1. Test changed and critical behavior proportionately, using 100% coverage only where the applicable repository contract requires it; never weaken tests or confuse a coverage number with behavioral confidence.
2. **Parallel Cloudflare Browser Run (`@cloudflare/playwright`) E2E Verification**: Full end-to-end journeys are executed in parallel using Cloudflare Browser Rendering (`@cloudflare/playwright` bound to `env.MYBROWSER` / `BROWSER`, with local multi-worker Playwright parity) across all **6 canonical breakpoints** (`320px`, `375px`, `768px`, `1024px`, `1440px`, `1920px`) and all **16 OKLCH interaction states**, providing near-100% E2E code and workflow coverage.
3. **Authorized Finish Line & Parallel End-of-Round Meaning Extraction Triad (`bin/triad-end-of-turn-sync.ts`)**:
   - Integrate, commit, push, deploy, mutate provider state, or purge caches only when current authority permits it. Otherwise finish and verify all reversible local work, preserve the exact tested tree, and report the single external gate.
   - **In parallel with final verification and reporting at the end of every prompt round**, run the **Parallel Meaning & Preference Triad Extractor** (`bin/triad-end-of-turn-sync.ts`) to harvest any possible meaning, preference, architectural lesson, reusable site code, or system configuration from the current agent window and store the value concurrently into:
     1. **`heymegabyte/agent-skills` (for AI skills, rules & agent master prompts)** — always updated under the **Minimum-Prompt Ecosystem Completeness Assumption**: assuming the skills *should have already been written* so that we write **as few prompts as possible (ideally one)** to finish **as complete a product (or entire multi-repo ecosystem) as possible** by automatically expanding scope and executing via **massive agent parallelization swarms** (`Claude` + `Codex` + `Gemini` + 80%+ `OpenCode` DeepSeek offload).
     2. **`heymegabyte/theme.tools` (for site & application code)** — extracting reusable UI components (16 states, `0.333s` OKLCH transitions), themes, calculators, workflows, validators, hooks, and plugin catalog adapters into the 28 canonical `@theme.tools/*` libraries.
     3. **`heymegabyte/install.doctor` (for system & host code)** — extracting reusable dotfiles, shell environment defaults, lazy CLI shims (`cnf-build-shims`), daemon units, and workstation/server provisioning code.
